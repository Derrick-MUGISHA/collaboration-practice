The branch names should clearly describe the work being performed so that other team members can understand what each branch is for.
Once a participant has created their branch, they begin implementing their task. They should first understand the existing code before changing it. They should look at the project's folder structure, existing components, naming conventions, and design system. If another participant has already created a reusable component that can be used, they should consider reusing it instead of creating a completely different version.
As participants work, they should regularly check their changes and test their work. They should avoid making unrelated changes to the project. If a participant is assigned to create a project card, for example, they should not suddenly rewrite the authentication system without discussing it with the team.
 
After selecting a task, participants do not immediately start working on the main branch. Instead, everyone creates their own feature branch. The branch represents the participant's workspace for a particular task.
A participant working on the navigation might create:
feature/navigation
Someone working on the project cards might create:
feature/project-cards
Someone working on authentication might create:
feature/login-form
Another participant working on responsive design might create:
fix/mobile-navigation
The important part of this activity is that everyone is working on one shared project. Students are not simply creating separate projects and submitting them individually. They are practicing how a real development team can coordinate many contributions inside one codebase.
At the beginning of the activity, the facilitator creates a GitHub repository for the project and gives everyone access to it. The repository becomes the central place where the team stores and manages the project. Each participant clones the repository to their own computer and prepares their development environment.
For example , five students might work on the landing page. One student could work on the hero section, another on the features section, another on testimonials, another on the call-to-action section, and another on making the entire landing page responsive. At the same time, another group could work on the dashboard, with different students responsible for the sidebar, header, statistics cards, tables, and profile components. Another group could work on authentication, while another group works on projects, events, or the contact system.
Imagine that our class has been hired as a software development team to build a modern website for a student technology community. The project will be developed by more than 25 participants, with everyone contributing to the same GitHub repository. Because there are many developers working on the project at the same time, the team needs a clear collaboration process to make sure that everyone's work can be developed, reviewed, and combined without creating unnecessary problems.
The project will contain many different parts. There will be a landing page, navigation, hero section, about section, services section, projects section, events section, courses section, testimonials, team members, contact section, authentication pages, dashboard pages, profile pages, reusable components, responsive layouts, forms, API integration, and other supporting features. Since there are more participants than major sections, some sections will have several students working on different parts of the same feature.
